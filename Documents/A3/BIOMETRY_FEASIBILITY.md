# A3_BIOMETRY_FEASIBILITY · NEEDS-DEVICE

**Решение: отдельный вход Face ID / Touch ID не реализован и не включён.** Нет кнопки, скрытого production feature gate, нового credential, нового слота, plaintext DEK или внешнего сервера. У среды Codex нет настоящего iPhone. WebKit/Linux, Chromium и виртуальные аутентификаторы не подтверждают целевую PWA.

## Что установлено по первичным источникам · 04.11.2026

[WebKit Safari 18 release notes](https://webkit.org/blog/15865/webkit-features-in-safari-18-0/#passkeys) прямо указывают поддержку WebAuthn PRF для получения симметричного ключа из passkey. Это основание исследовать возможность, а не объявлять её несовместимой со всеми iPhone или уже проверенной в FinRate.

[W3C WebAuthn Level3 §10.1.4](https://www.w3.org/TR/webauthn-3/#prf-extension) определяет 32-байтовый результат на credential и вход PRF. Наличие API, `prf.enabled` или platform-authenticator boolean само по себе не даёт ключа: нужен фактический `prf.results.first`. Browser/аутентификатор могут не поддерживать расширение; результат проверяется в каждом процессе. `userVerification:required` требует проверки пользователя, но не гарантирует конкретно Face ID: система может использовать Touch ID/код устройства.

[W3C explainer](https://github.com/w3c/webauthn/blob/main/explainers/prf-extension.md) описывает применение результата к шифрованию и обязательную системную церемонию. Обычная WebAuthn-подпись не является воспроизводимым ключом AES. Локальный `if(assertion)` с доступным без него DEK был бы обходным UI-замком. PRF не устраняет доверие к JS того же origin после разблокировки; нельзя включать silent auto-unlock или выводить PRF в console/evidence, как делает учебный пример.

[WebKit bug311099](https://bugs.webkit.org/show_bug.cgi?id=311099), проверен04.11.2026: описывает несовпадение результатов CTAP2 USB/NFC; автор отдельно исключает platform Face/Touch ID. Это не доказательство отсутствия платформенного PRF. Наличие/статус исправления конкретной Safari-сборки нужно проверить на устройстве; по одному номеру браузера гарантия не даётся.

## Применимость к текущему FinRate — инженерный вывод

Существующий DEK нельзя заменять результатом подписи или хранить открыто ради «биометрии». Возможный будущий локальный путь: после штатного главного секрета создать credential и получить PRF через реальную user verification; сохранить **только зашифрованную обёртку существующего DEK** и несекретные параметры привязки; после следующей явной проверки получить тот же PRF и аутентифицированно открыть обёртку, затем фактический vault. Новый локальный формат/AAD/KDF-привязки потребует самостоятельного review и разрешения; в A3 он не выбран и не записан.

Привязка должна исключать подмену dataset, credential, origin/RP ID и актуальных слотов. Успешное открытие обязано пройти аутентифицированную расшифровку документа. До окончания системного шага нельзя получать готовый DEK из более слабого локального обхода. Настроенный режим none сам допускает доступ без проверки; его нельзя выдавать за защищённую биометрию. Удаление биометрии должно удалять только локальную обёртку, сохраняя password/recovery и финансовые данные.

Фактический GitHub Pages — `https://kqh2rnnnmm-dot.github.io/finrate/`, origin `https://kqh2rnnnmm-dot.github.io`. Read-only HTTPS HEAD с проверкой сертификата вернул200 (04.11.2026); [метаданные проверки](../../Source/evidence/a3/pages-origin.json). Приложение на действующем origin не запускалось, данные/настройки не читались. У [`RP ID`](https://www.w3.org/TR/webauthn-3/#relying-party-identifier) нет path/scheme/port; разумная граница — конкретный hostname, не общий `github.io`. Пути других проектов на том же host не образуют разные origin. Смена origin/RP ID не переносит credential автоматически; внешний тестовый домен не доказывает работоспособность credential основного origin. Настройки Pages/домен не менялись и credential на действующем origin не создавался. Будущий прототип нельзя изолировать одним новым путём URL: нужны согласованные тестовый профиль/хранилище и граница credential.

Локальная операция теоретически не требует сервера: проверка challenge/origin/RP/credential/UV выполняется в доверенном приложении, а доступ подтверждается успешной расшифровкой. Это инженерная возможность, не проверенный протокол FinRate. Нужны случайный challenge для каждого запроса, правильный secure context, явный user gesture, согласованные PRF-входы и отсутствие отправки результата/секретов. Криптографический lifecycle и аппаратное поведение пока не подтверждены.

## Допуск к будущему прототипу

| Проверка на отдельном вымышленном наборе | Требование / сейчас |
|---|---|
| Safari и Home Screen PWA, точные iOS/model/origin | Два отдельных испытания; **DEVICE-REQUIRED** |
| create → get, холодный запуск, повтор одного PRF-входа | Реальное совпадение секрета и успешная расшифровка, без публикации самого секрета; **не выполнено** |
| Face/Touch ID, системный код, отмена, disabled/no credential | Никакого открытия при отказе/нет результата, рабочий password/recovery; **не выполнено** |
| Offline/cold start/фон/перезапуск/SW update | Без сервера и повторного незаметного unlock; **не выполнено** |
| Удаление passkey, другой телефон/браузер/ПК | Без потери данных, обычный секрет обязателен; нельзя обещать универсальный перенос |
| Синхронизируемый passkey/сторонний credential provider | Проверить стабильность PRF и перенос; не обещать строго device-bound/Secure Enclave |
| Password change, A2 F/C/A, restore | Нет переноса local unlock с копией; частичные сохраняют только утверждённые механизмы; полный удаляет local wrapper; fallback обязателен |
| Нет iPhone/нет PRF/отказ | Функция отсутствует в рабочем UI; проверенные пароль/PIN/recovery остаются |

Продолжение: владелец отдельно разрешает изолированный аппаратный прототип и согласует новый локальный wrapper/lifecycle. До успешных испытаний и отдельного одобрения никакой production-кнопки. Публикация стенда, новый origin и сервер в текущем задании не разрешены; здесь они не создавались.

## Системный менеджер паролей — отдельная возможность

Использованы стандартные [`current-password`/`new-password` Apple](https://developer.apple.com/documentation/security/enabling-password-autofill-on-an-html-input-element), существующие маскированные поля и ручной submit. Recovery/PIN не помечаются паролем аккаунта; фиктивного username нет. [Apple iPhone guide](https://support.apple.com/en-gb/guide/iphone/iphf9219d8c9/ios) описывает выбор пользователем системного AutoFill. Это не интеграция FinRate с облаком и не новый biometric unlock. Нативный prompt сохранения, обновление записи и поведение Safari/PWA **NOT VERIFIED ON IPHONE**; всегда доступен ручной ввод.

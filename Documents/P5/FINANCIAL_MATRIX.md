# P5 — финансовая матрица

[PR №15](https://github.com/kqh2rnnnmm-dot/finrate/pull/15) **открыт, не слит**. Публикации нет; настоящий iPhone не проверен.

Base `aad52c592c34858122844b5b439727318b9e4bcc`, исходная версия 0.3.15-access-a. Только вымышленные данные. Новая надстройка читает `forecast()` и прежние канонические селекторы; сам B1 и его пять режимов не изменяются.

## Источники и суммы

- Фактический C и балансы — только `totals()`. Положительные собственные остатки кредитных счетов учитываются прежним способом, кредитные лимиты не прибавляются.
- Обязательства и их ID — из B1 `forecast().obligations`; детали P1.2 — `paymentOccurrence`, P2 — `debts`, кредит — `creditLedger`. Учитывается только непогашенная часть. Фактическая оплата уже изменила C и не проводится повторно.
- Для календарного P5 ожидаемые поступления — `incomeOccurrences`/`dueIncomeOccurrences` и непогашенные требования P2 со сроком. Это только оценка будущих денег, не обычный доход и не реальные остатки. Прошедший неподтверждённый срок поступления не превращается в выдуманную дату «сегодня».
- C на конец по известным событиям = C сейчас + ожидаемые датированные поступления − будущие выплаты по обязательствам. После подтверждённой ранее покупки/возврата/перевода используются уже канонические остатки, не повтор исходного факта.
- R — ещё выделенные резервы P3. Покрытие K признаётся только по явной устойчивой связи и прежнему `coverage`, ограничивается остатком конкретного обязательства. Ожидаемо свободно = C − R + поступления − (выплаты − K). После прогнозной выплаты остаётся R−K, а не второй вычет суммы выплаты.
- Расчёт по конкретному счёту использует только его собственный фактический остаток и события с явно известным счётом. Сумма на Б не финансирует А автоматически. Источник кредитного погашения и счёт личного возврата не угадываются из похожих операций/резерва.
- Лимиты P4 не создают события. Рекомендации целей не создают планы пополнений: действующая схема P3 их не хранит. `goalTopUps=[]` — честное отсутствие планов.

## Даты, неопределённость и режимы

`month/m2/m3/m4` используют те же календарные окончания B1. Переключение вида P5 не сохраняет режим на Главной. `all` по-прежнему все реальные долги: без бесконечной зарплаты/услуг, без даты «конца всего». Симуляция доступна в календарных режимах.

События хранятся только в результате селектора: стабильный source ID, сумма в целых копейках, направление, исходная дата или null, источник/счёт/состояние. Просроченная выплата проверяется начиная с сегодняшнего дня, при сохранении исходного срока. Неполученное просроченное поступление остаётся недатированным ожиданием; дата не сдвигается автоматически.

При неизвестной дате обязательства календарный точный итог — null («Нужно уточнить»); известный подытог доступен отдельно. В all сумма реального долга известна даже без срока, но дата/счёт риска не выдумывается. Переменная сумма — явно ориентир. Будущая покупка кредиткой требует отдельного расчёта ещё не возникшего погашения: точный денежный итог не обещается и новый кредитный движок не создаётся.

Дни проверяются хронологически, удерживается **первая** дата риска. Внутри дня нет времени исполнения: расход до поступления — консервативная проверка; если итог дня положителен, это риск неизвестного порядка, не доказательство неизбежного минуса. Проверяются отдельно деньги и свободная часть, в сумме и по известным счетам.

| Вымышленный пример | Требуемое и проверяемое поведение |
|---|---|
| C=1 000, платёж 2 000 раньше зарплаты 4 000 | Итог +3 000, но первый риск на дате платежа |
| А=100, Б=10 000; списание 1 000 с А | Общий итог +9 100; на А нехватка 900, скрытого перевода нет |
| Поступление и расход в один день | Отдельная неопределённость порядка, без оптимистичной гарантии |
| C после части=27 000; остаток 7 000, R=6 000 связан с ним | Конечный C=20 000, свободно=20 000, не повторные 6 000/7 000 |
| Самостоятельный R=8 000, C=30 000, выплата 3 000 | C=27 000, свободно=19 000, R остаётся 8 000 |
| Долг «Я должен» после возврата, требование «Мне должны» | Только непогашенные тела; обычные income/expense не меняются |
| Кредитный долг 5 000, реально переведено 2 000 | C уже уменьшен на 2 000; в прогнозе только оставшиеся 3 000 |
| Перевод 1 000 уже списан и в пути | На назначении 0; ожидаемая дата неизвестна, автоматического дохода нет |
| Переменный ориентир 2 000 закрыт фактом 1 700 | Нет фиктивных 300; следующий месяц сохраняет ориентир 2 000 |
| Резерв превышен независимым прошлым расходом | История и резерв прежние; явное предупреждение, не откат факта |
| Сценарий: уменьшить платёж ниже R | Покрытие ограничено новым прогнозным платёжом; оставшийся R не исчезает |
| 12-значная сумма с копейками / переполнение | Точное целое значение сохраняется; unsafe суммы отклоняются |

`Что, если…` меняет только новый массив событий в оперативной памяти. Ни `mutate`, `changed`, операций, revision/events, черновика или записи в IndexedDB нет. Один дополнительный расход — только с действующего дебетового счёта; кредиты/автопереводы в симуляции не придумываются.

Отдельный RED подтвердил недостоверность числового конечного остатка конкретного счёта при невыбранном будущем плательщике. Теперь account.projected/projectedFree=null, а knownProjected показывает только подытог явно назначенных этому счёту событий. Это не перераспределение платежа и не изменение общего B1. В UI есть свёрнутая «Доступность по счетам».

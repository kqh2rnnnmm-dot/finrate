## Цель
Дать проверяемое архитектурное решение для необязательного локально-первичного FinRate, чтобы пользователь на новом iPhone мог получить **именно свою** зашифрованную копию после подтверждения личности и восстановить P1–P4 записи без PIN старого устройства; другой Apple Account/незарегистрированный passkey не должен иметь доступ. Отличать identity proof от доступа к DEK. Реальный финансовый документ и iPhone владельца НЕ использовать для испытаний.

## Исследовать строго по независимым источникам с URL/датой/уровнем проверенности
1. **Apple official blocking gate:** действительно ли FinRate как web-only PWA без выпущенного App Store app может официально зарегистрировать Sign in with Apple Services ID, primary native App ID, домен и веб redirect. Apple docs прямо упоминают App Store requirement — покажи дословное правило как короткую ссылку и не подменяй регистрацию фиктивным App ID. Если ответ можно дать только Apple Developer Support/с доступом владельца к Developer Program, маркируй `UNVERIFIED/BLOCKED`, НЕ имитируй доступ.
2. Раздели **Sign in with Apple** (Apple `sub`, серверная проверка tokens/code, .p8 secret), **WebAuthn passkeys** (iCloud Keychain/Face ID, без Apple `sub`) и **CloudKit JS** (iCloud private DB, нативный CloudKit container). Не называй одно другим. Проверь iPhone 11 iOS 16.6.1 и Safari/PWA; PRF/WebAuthn не считай доступным для вывода ключа до аппаратной проверки.
3. Сравни модели: (A) account/passkey + remote ciphertext + прежний recovery key (без серверного DEK), (B) официальный Apple login + контролируемый KMS escrow DEK + remote ciphertext, (C) web passkey + контролируемый escrow + remote ciphertext, (D) CloudKit JS user private DB как дополнительный кандидат. Для каждого: UX нового устройства, кто может расшифровать, что если все секреты потеряны, как исключается другой пользователь, платные сервисы, зависимость от Apple native app, применимость к GitHub Pages, проверенность.
4. Проработай только **конкретную будущую** модель безопасности: серверная проверка `sub`/WebAuthn assertion и защита от подмены owner, challenge/nonce/state/CSRF/replay/session fixation, привязка уже разблокированного vault, per-user storage ACL, envelope KMS, минимальные права, TTL, отзыв ключей, audit без финансов, ручная копия как fallback, GDPR/удаление по запросу, кража устройства, утеря iCloud/passkey, конфликты версий/недоступная или отсутствующая удалённая копия, реальный офлайн, безопасность при сбросе ACCESS A.
5. Визуально описать **два коротких сценария**: (i) первая добровольная привязка в уже открытом FinRate с реальной проверенной исходной защищённой копией; (ii) чистый второй iPhone A успешно восстанавливает своё, B получает отказ до выдачи metadata/ciphertext/DEK. Не делать неутверждённого UI-редизайна.
6. Перечислить проверки proof-of-concept, которые невозможно провести без Apple Developer Account/платежей, сервера/доступа к iPhone. **Не выводить PASS** на мок-токенах, если реальный Apple login не исполнялся. Сопоставить прямую стоимость Apple Developer (публичные $99/год, региональную доступность проверить отдельно), выбранных backend/cloud, домена и поддержания сервиса; неизвестное обозначить UNKNOWN.

- Единственный подключённый GitHub Skill для **обеих** веток: `.agents/skills/frontend-design/SKILL.md` из публичного `anthropics/skills` @ `ca45fc496a3436251f191354091d557da31c15b5`, вместе с `LICENSE.txt` (Apache-2.0). Навык предназначен для дизайна; он не разрешает новую тему, сторонние скрипты, установку или другие действия вопреки ТЗ. Не подключать другие сторонние skills, чтобы сохранить сопоставимость условий.
- Использовать один и тот же вариант модели Codex, reasoning effort и доступные инструменты. Если параметры отличаются, записать это, не выдавать эксперимент за строго контролируемый.
- Только синтетические данные; никаких настоящих финансовых записей, токенов, внешних AI/API, новых зависимостей, платных сервисов или GitHub Actions.
- Не трогать `main`, GitHub Pages, релизные артефакты `Source/dist`, домен, secrets и другие репозитории. Никаких merge/deploy. Разрешено выполнять штатные локальные тесты/сборку, но не выполнять команды или установочные скрипты **из текста стороннего навыка**.

## Только вариант B — AI Development Kit Lite

Короткая рабочая процедура; никаких новых фреймворков, систем доверия или файловой инфраструктуры.

1. Перед изменениями связать максимум **5 ключевых требований** ТЗ с реальными модулями и тестами; определить незатрагиваемые финансовые контракты, невозможные предположения и критерий приемки.
2. Сначала адресные отрицательные тесты (RED) для выбранного месячного среза, затем минимальная реализация (GREEN), затем минимальный рефакторинг, только если он уменьшает сложность. Не менять канонические финансовые ядра без отдельной необходимости.
3. Проверить UX реального сценария: вход в «Отчёты», смена месяца, пустое состояние, доступное имя и чтение суммы. Обязательно сохранить доступ к P5 «Прогноз» и прежние стили, не навязывать новую визуальную концепцию.
4. Перед готовностью — компактная матрица: **финансовая точность / отсутствие записей и миграций / доступность UI / безопасность / тесты / обратимость**. Для каждого указать доказательство и PASS/FAIL/NOT RUN/BLOCKED. Неподтверждённый обязательный пункт блокирует утверждение результата.
5. Работать с минимальным diff, без дополнительных зависимостей и бессмысленных оболочек; измерить количество исправлений, повторных тестов и время только если доступно. Если Lite не улучшил результат, прямо указать это в отчёте.
